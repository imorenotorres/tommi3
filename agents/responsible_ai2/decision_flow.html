Data Architecture

Three JSON files provide all structured metadata, loaded once at startup and cached in memory.

Keyed by university. Per paper: id, title, abstract, authors, affiliations, concepts, doi, publication_date/year, cited_by_count, pdf_url

researchers.json cached
Keyed by university. Per researcher: name, affiliations (per-author), affiliation_status, topics, papers [{id, title, year}]

config.json cached
agent_name, research_topic, alliance, universities {acronym: {name, country, lat, lon}}

PDFs from data/docs/ chunked & embedded (all-MiniLM-L6-v2). Per-chunk metadata: source, title, author, university
Fallback for open-ended content questions

4. Load researchers.json378 researchers → self._researchers_by_uni
5. Initialize ChromaDBSync PDFs, chunk & embed new documents
6. RAG configChunk size, overlap, retrieval count from env

② Query Processing (per user message)

Six conditions evaluated in order. First match wins — all YES paths feed their context into ③ LLM Call (via the purple merge line on the right). The NO path continues down to the next step.

③ LLM Call

System prompt + selected context + conversation history + user message
Model: Mistral (cloud/Ollama) · Max tokens: 16,384

④ Lightweight Grounding Check

Extracts verifiable claims from the LLM response (titles, authors, years, university acronyms, paper IDs, bold text).
Each claim is checked against Metadata context (keyword search results) and RAG context (retrieved chunks).
Result: percentage breakdown — Metadata: X% | Database: Y% | LLM: Z%

④b Badge Decision

Special cases (checked first):
• Figure/map request → always 🟢 Green
• Follow-up query with history → no badge
• Gap analysis ("topics not studied") → always 🔴 Red (LLM: 100%)
• "Not found" response with LLM: 100% → 🟢 Green (database confirmed absence)

Threshold-based (from config.json):
• LLM ≤ reliability_green_max_llm (default 20%) → 🟢 Green
• LLM < reliability_red_min_llm (default 50%) → 🟡 Yellow
• LLM ≥ reliability_red_min_llm → 🔴 Red

Grounding check: After the LLM generates its response, verifiable claims (titles, authors, years, etc.) are extracted and checked against the metadata and RAG contexts. The badge colour is determined by the LLM percentage: 🟢 LLM ≤ 20% → High  |  🟡 LLM 21–49% → Good  |  🔴 LLM ≥ 50% → Poor. Thresholds are configurable in config.json.

Reliability Configuration (config.json)

ParameterDefaultDescription
reliability_green_max_llm20Max LLM % for 🟢 green badge (High reliability)
reliability_red_min_llm50Min LLM % for 🔴 red badge (Poor reliability)
The lightweight grounding check extracts verifiable claims (quoted titles, bold text, author names, years, university acronyms, paper IDs) from the LLM response and checks each against the metadata context and RAG context. Claims found in either are grounded; claims not found are attributed to the LLM. No additional LLM call is needed — it is pure string matching and runs in milliseconds.

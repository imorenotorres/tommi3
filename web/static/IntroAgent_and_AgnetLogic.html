Understanding AI Agents and Agent Workflows

An AI Agent is a flexible, autonomous software system that facilitates the interaction between users and computer systems. Unlike traditional applications with rigid interfaces, AI Agents may accept different input types, including natural language, interpret the user's intent, execute the appropriate actions, and deliver results — adapting their behaviour to each situation.

This document first presents a general model for AI Agents. It then shows how each stage of the model is implemented as code components in the TOMMI Agentic Platform. Finally, it describes the different types of agents available in the platform.

Part 1 — A General Model for AI Agents

How do AI Agents work?

According to the classic AI agent framework (Russell & Norvig, 1995) [2], every agent follows three basic stages: Perception → Reasoning → Action. Here, we add a fourth stage — Production — to distinguish executing the task (e.g., querying a database, calling a language model) from producing the output (e.g., rendering a map, formatting a table, adding reliability indicators). Thus, according to this proposal, the stages of every AI agent are the following:

Intuitive Examples of Each Stage

StageWhat happensEveryday analogy
1. Perception The agent accepts the user's input: a typed question, a button click, a form selection, or a voice command. A librarian hears your question at the desk.
2. Reasoning The agent analyses the input to understand what the user wants and decides which action to take. This may be trivial (pass to the LLM) or complex (classify the query type, select data sources, detect intent). The librarian decides whether to look in the catalogue, the encyclopaedia, the archives, or simply answer from memory.
3. Action The agent executes one or more actions: query a database, search documents, call a language model, generate a chart, compute a result, or decline a request. The librarian walks to the shelf, finds the book, and reads the relevant passage.
4. Production The agent produces the output for the user: text, a table, a map, a chart, or a polite explanation of why it cannot help. A reliability indicator may be added. The output format depends on the interface and the type of result. The librarian returns to the desk and gives you the answer, noting whether it came from a trusted reference or a less reliable source.

Not every agent uses artificial intelligence in every stage. Some agents use AI only for Reasoning (understanding the question), others use it only for Action (generating text), and some use no AI at all — relying on rules and structured data throughout.

Note: This four-stage model is a conceptual abstraction for understanding agent behaviour. In practice, the boundaries between stages may overlap — for example, context retrieval serves both Reasoning (deciding what is relevant) and Action (querying a data store). Simpler agents may have minimal Reasoning, while complex agents may interleave multiple stages. The model is most useful as a framework for explaining what an agent does, not as a rigid architectural blueprint.

1. Perception

The agent receives the user's text query via the chat interface. It also receives session context: conversation history, session ID, model preference, and transparency level. LLM: Not used.

2. Reasoning

Before classification, the query is normalised: a synonym expansion step replaces common variants with canonical terms (e.g., "publications" → "papers", "visualise" → "figure", "define" → "what is") and strips academic titles ("Professor", "Dr."). Researcher name matching is accent-insensitive ("Ruben Gonzalez" matches "Rubén González"). A priority chain of 13 classification checks then identifies which response path the query should follow. The first match wins. The entire chain is rule-based and deterministic. LLM: Not used.

1. Perception

The agent receives the user's text query via the chat interface.

2. Reasoning

The query is converted into a vector embedding and used to search ChromaDB for semantically similar document chunks. This is mechanical — no classification of query type, no decision-making. LLM: Not used (embedding model is separate from the generative LLM).

3. Action

LLM: Always used. The LLM receives three inputs combined into a single prompt: the system prompt (agent identity and rules), the retrieved document chunks (context), and the user's query. The LLM generates an answer constrained to this context. Every query goes to the LLM — there is no programmatic path.

Example: what the LLM receives

For a query like "What is explainable AI?" on a Responsible AI agent, the LLM prompt is assembled as follows:

── System prompt (from prompts.json) ────────────── You are a research assistant for the UNINOVIS Excellence Hub on Responsible AI. Answer only from the provided context. If the answer is not in the context, say so. ── Retrieved chunks (from ChromaDB / BM25) ──────── --- Chunk 1 --- Explainable AI (XAI) refers to methods and techniques that make the outputs of AI systems understandable to humans. The EU AI Act requires high-risk AI systems to provide explanations of their decisions... --- Chunk 2 --- Key XAI techniques include LIME (Local Interpretable Model-agnostic Explanations), SHAP (SHapley Additive exPlanations), and attention visualisation... --- Chunk 3 --- The relationship between explainability and trust is well documented. Users who understand why an AI system made a decision are more likely to trust it... ── User query ────────────────────────────────────── What is explainable AI?

The LLM can only "see" the content above. It cannot access the database, the internet, or any other data. The quality of the response depends entirely on whether the retrieved chunks contain relevant information.

4. Production

The LLM response is post-processed (humility hedging, authority sanitisation) and delivered with a reliability cue. LLM: Not used — post-processing is rule-based.

1. Perception

The agent receives the user's text query via the chat interface.

2. Reasoning

The query is tokenised (split into words, stop words removed) and scored against all document chunks using BM25 keyword matching. The top N chunks with the highest scores are selected as context. This is mechanical — no classification of query type. LLM: Not used.

LLM: Always used. The LLM generates an answer constrained to this context. Every query goes to the LLM — there is no programmatic path.

Example: what the LLM receives

For a query like "How do I deploy an agent?" on the Tommi Tutor agent, the LLM prompt is assembled as follows:

── System prompt (from prompts.json) ────────────── You are Tommi Tutor, a support assistant for the TOMMI Agentic Platform. Answer questions about deploying, configuring, and testing AI agents. Use only the provided context. ── Retrieved chunks (BM25 keyword match) ────────── --- Chunk 1 (score: 8.4) --- To deploy an agent, create a directory under agents/ with agent.py, app.py, config.json, and prompts.json. The config.json file defines the agent's name, type, LLM provider, and data sources... --- Chunk 2 (score: 6.1) --- After creating the agent files, register it in the web server by adding an import and mount statement in web/app.py. Restart the server to load the new agent... --- Chunk 3 (score: 4.7) --- Agent types available: rag_vectorless (BM25 keyword retrieval), rag_metadata_vectorless (structured metadata + BM25), text2sql (natural language to SQL), oneshot (no retrieval)... ── User query ────────────────────────────────────── How do I deploy an agent?

Unlike ChromaDB (vector search), BM25 matches chunks by keyword overlap — the query words "deploy" and "agent" match directly against the chunk text. Chunks are ranked by BM25 score and the top N are selected. The LLM can only "see" these chunks and must answer from them.

4. Production

The first 300 characters of the response are checked for off-topic refusal phrases. If detected, no banner is shown (honest refusal). Otherwise, a yellow "AI Commentary" banner is added. LLM: Not used — post-processing is rule-based.

When to use Oneshot

Oneshot agents are appropriate when:

  • The task does not require a knowledge base (e.g., prompt writing, brainstorming)
  • Each query is self-contained — no follow-up needed
  • The LLM's general knowledge is sufficient
  • Speed is important (no retrieval overhead)

For tasks requiring grounded, verifiable answers from specific data, use RAG or Metadata+RAG agents instead.

Key Insights for Agent Design

Handling Reliability

Reliability is a central challenge in AI agent design. As Rabanser et al. (2025) argue, "reliability is not a single property but a multidimensional concept" that encompasses correctness, consistency, robustness, and transparency [1]. An agent may produce a correct answer for one query and hallucinate on a similar one — and the user has no way to tell the difference unless the system provides reliability signals.

In the TOMMI platform, reliability is addressed through two complementary mechanisms: (1) minimising LLM dependence by routing queries to programmatic, deterministic response paths whenever possible, and (2) reliability cues — visual indicators that communicate to the user how much the response depends on AI interpretation vs. verified data. The cue colour reflects the structural grounding of the response path, not a confidence score.

The reliability of an AI agent's response correlates with the amount of relevant, controlled context provided to the LLM. Three factors determine this:

FactorDescriptionEffect on reliability
Context relevanceDoes the injected context (retrieved chunks, glossary entries, paper data) match the user's query?High relevance → LLM is constrained to accurate information → lower hallucination risk
Context volumeHow much relevant data is injected into the LLM prompt?More relevant context → LLM has more material to draw from → less need to invent
Instruction qualityHow well do the system prompt rules constrain the LLM? (e.g., "only answer from provided context", "say you don't know if uncertain")Stricter rules → LLM less likely to hallucinate beyond the context

This suggests a spectrum from green (fully grounded) to red (poorly grounded):

CueGrounding levelExamples
GreenProgrammatic. The response is built directly from structured data files, without involving the LLM. Since no AI interpretation is involved, the response is 100% faithful to the source data."Papers by Rubén González" → the agent looks up the name in a researchers file and returns the exact list of papers stored there.

"What is explainable AI?" → the agent finds the term in a curated glossary and returns the expert-written definition verbatim.
YellowLLM well-grounded. The LLM generates the response, but it has been given relevant data as context. The AI interprets and summarises this data, so the response is informed but may not be perfectly faithful."What are the main research topics at THUAS?" → the agent retrieves relevant papers and provides them to the LLM, which writes a summary. The paper list is real, but the summary is AI interpretation.
RedLLM poorly grounded. The topic has little or no representation in the available data. The LLM must reason from general knowledge or infer what is absent — both inherently speculative."What responsible AI topics have not been studied?" → the LLM must reason about what is missing from the database — a speculative task with high hallucination risk.

A note on dynamic scoring

At least theoretically, reliability could be computed dynamically — for example, based on the number of retrieved chunks or their relevance scores. However, this would introduce instability (the same query could get different cues each time), arbitrary thresholds, and user confusion. It would also create a transparency paradox: a black-box estimation inside the transparency system itself. Instead, TOMMI assigns cues based on query type, which is determined by the deterministic classification chain — making the cue predictable, explainable, and stable.

The four dimensions of reliability

Rabanser et al. [1] identify four dimensions of AI agent reliability. The following table analyses how each is addressed in TOMMI:

  • Paper verification checks every cited title against papers.json.
  • SQL verification checks table/column existence and semantic alignment.

This could be reduced by making the LLM more deterministic (setting temperature=0) or by storing previous answers (caching). The more response paths are programmatic, the more consistent the agent is overall.

  • Crystal box mode shows generated SQL for verification.
  • Open documentation makes the decision process auditable.

The key insight is that programmatic response paths score high on all four dimensions simultaneously: correct, consistent, robust, and transparent. Each query moved from an LLM path to a programmatic path improves reliability across all dimensions at once.

Example: a real failure analysed through the four dimensions

A user types "Things by topic" — a vague, possibly accidental query. The agent correctly reports "No papers found" (the topic search returns 0 results). However, it then calls the LLM for commentary. Since the LLM has no data to work with, it fabricates a lengthy analysis discussing universities, research themes, and collaborations that have nothing to do with the query.

DimensionHow this failure manifests
SafetyCompliance violation. The agent's constraint is "only answer from provided context." The context was empty (0 papers), yet the LLM produced unsolicited, ungrounded content. A user might mistake this fabricated analysis for real findings.
PredictabilityUnpredictable behaviour. The user cannot anticipate when the agent will produce grounded vs fabricated commentary. A "0 results" response should be a clear signal that no analysis is possible — but the agent contradicts its own finding.
ConsistencyInconsistent framing. The factual section says "No papers found" while the commentary discusses research themes as if data exists. The two parts of the same response contradict each other.
CorrectnessFabricated content. The commentary mentions specific universities, topics, and collaboration patterns that are not grounded in any data.

The fix: When a data search returns 0 results, the agent now returns the factual "No papers found" message and skips the LLM commentary entirely. This converts a mixed path (programmatic data + LLM commentary) into a purely programmatic path for the empty-results case — eliminating the fabrication risk at its source. This is an example of extending the programmatic boundary: identifying a case where the LLM adds no value and removing it from the response path.

Example: a false-positive match

A user types "Things to do" — clearly not a research query. The topic extraction accepts it as a bare topic phrase (3 words, no question word). The search matches "Things" against a paper about the "Internet of Things" (IoT). The agent then presents this paper with a Green cue ("Verified data") — misleading the user into trusting a spurious match — followed by LLM commentary that tries to rationalise "Things to do" as a research topic.

DimensionHow this failure manifests
RobustnessPrimary failure. The topic extraction was too permissive — it accepted vague everyday phrases as research topics and matched partial words against paper metadata.
SafetyMisleading cue. A Green cue is assigned to a false-positive match, undermining the user's trust in the cue system. If green can be wrong, all cues lose credibility.
CorrectnessWrong match. The paper is real but the match is spurious — it is not about "Things to do."

The fix: The topic extraction now rejects queries that consist entirely of generic/common words (e.g., "things", "stuff", "something") and maintains a blocklist of clearly non-research phrases ("things to do", "help me", "hello"). This is a robustness improvement: the classification chain becomes less brittle to vague or accidental inputs, preventing false-positive matches that cascade into misleading results and fabricated commentary.

Choosing the Right Agent Type

The choice of agent type should be driven by three questions about your specific use case:

Question 1: What kind of data do you have?

Your dataRecommended typeWhy
No data — the LLM's general knowledge is sufficientOneshotNo retrieval overhead. The system prompt defines the agent's expertise. Suitable for creative tasks, prompt design, brainstorming.
Unstructured documents (PDFs, markdown, web pages)RAG or RAG VectorlessDocuments are chunked and searched. RAG (vector) for semantic queries; RAG Vectorless (BM25) for keyword-rich content or simpler setups.
A structured database (SQLite, PostgreSQL)Text2SQLThe LLM translates questions to SQL. Results come directly from the database — factual and precise.
Structured metadata (JSON) + unstructured documents + glossariesMetadata+RAGThe most capable type. Combines programmatic responses for structured data with LLM-based responses for open-ended queries.

Question 2: What kind of queries will users ask?

Factual questions about documents ("What does the policy say about X?")RAG / RAG VectorlessThe answer is in the documents. Retrieval finds the relevant passages.
Quantitative queries about structured data ("How many agreements with Germany?")Text2SQLSQL can express filters, counts, and aggregations precisely.
Mixed: factual lookups + conceptual questions + data explorationMetadata+RAGDifferent query types need different response paths. The classification chain routes each query optimally.

Question 3: How important is reliability?

How Reasoning complexity varies

The choice of agent type directly determines the complexity of the Reasoning stage — which is where the most significant architectural differences emerge:

Agent typeReasoningResponse pathsLLM usage
Oneshot None — every query follows the same path 1 Always (100%)
RAG / RAG Vectorless Mechanical retrieval (vector or keyword) 2 Always (100%)
Text2SQL 8-step intent detection chain 8 New queries only (~25%)
Metadata+RAG Synonym normalisation + 13-step classification chain + 5-step content sub-chain 18 5 of 18 paths (~28%)

More response paths mean more development effort, but also higher reliability and lower LLM costs. The trade-off is explicit: each programmatic path added is one fewer query that needs the LLM.

Critical Architectural Elements

Regardless of agent type, three architectural elements determine the quality of the agent's responses. Getting these right is more important than the choice of agent type itself.

System Prompts

The system prompt is the single most important element of any agent. It defines who the agent is, what it can do, and how it should behave. In TOMMI, system prompts are stored in prompts.json and structured into three sections, activated by the prompt level setting:

SectionActive atPurposeExample content
Identity All levels Defines who the agent is and its core purpose. Always present. "You are a research assistant for the UNINOVIS Excellence Hub on Responsible AI. You help users explore research publications, projects, and researchers."
Rules Tolerant, Stringent Behavioural guidelines: tone, communication style, what to include/exclude in responses. "Always cite the paper title and authors when referencing a publication. Never invent paper titles. If you are unsure, say so."
Strict Stringent only Hard limits, prohibitions, and fallback instructions. The strongest constraints. "NEVER claim that a topic has not been studied unless the database search returned zero results. NEVER generate citation counts — the database does not contain this information."

Guidelines for writing effective system prompts

  • Be specific, not generic. "You are a helpful assistant" is weak. "You are a research assistant specialising in responsible AI publications from 7 European universities" is strong — it constrains the LLM's scope.
  • Define the boundaries explicitly. State what the agent should NOT do: "Do not write essays, translate text, or answer questions outside your domain."
  • Specify the output format. "Present results as a numbered list with title, authors, and year" gives the LLM a clear template.
  • Anticipate failure modes. "If you cannot find the answer in the provided context, say 'This topic does not appear in the indexed database' rather than guessing."
  • Use the Strict section for hard rules. Rules like "NEVER invent paper titles" should be in the Strict section, not in the general Rules — they must be enforced even when the LLM is tempted to fill gaps.
  • Test with adversarial queries. Try queries designed to break the agent: off-topic requests, ambiguous phrasing, requests for information that doesn't exist.

Knowledge Base Design

For RAG, RAG Vectorless, and Metadata+RAG agents, the knowledge base is the second critical element. The LLM can only answer from what it is given — poor knowledge base design leads to poor answers.

DecisionOptionsTrade-offs
Retrieval method BM25 (keyword) vs ChromaDB (vector) BM25 is simpler, faster, and requires no dependencies — but only matches exact words. ChromaDB finds semantically similar content ("adversarial testing" matches "red-teaming") but requires an embedding model.
Chunk size Small (100–200 words) vs Large (500–1000 words) Small chunks are more precise but may lack context. Large chunks provide more context but may include irrelevant text. Typical: 300–500 words with 50-word overlap.
Number of chunks retrieved Few (3–5) vs Many (10–20) Fewer chunks = less noise but risk missing relevant content. More chunks = better coverage but more LLM cost and potential confusion. Start with 5, tune based on results.
Data format Unstructured (documents) vs Structured (JSON, DB) Unstructured data must be chunked and retrieved — the LLM interprets it (yellow cue). Structured data can be served programmatically — no LLM needed (green cue). Use structured data wherever possible.

Response Path Design

A response path is the complete route a query takes through the four stages (Perception → Reasoning → Action → Production). The number and kind of response paths determine the agent's reliability and efficiency.

When designing response paths, consider:

  • Which queries can be answered without the LLM? Every programmatic path is faster, cheaper, and 100% reliable. Common candidates: meta-questions ("What can you do?"), refusals (off-topic, non-research tasks), lookups in structured data (researcher, project, glossary).
  • Which queries need the LLM but can be grounded? Provide as much relevant context as possible. Topic searches, for example, can combine a programmatic paper list (green) with LLM commentary (yellow).
  • Which queries are inherently speculative? Gap analysis, conceptual questions outside the glossary, and follow-ups without context are poorly grounded — assign red cues and consider whether these paths are worth supporting.
  • What reliability cue does each path get? The cue should reflect the structural grounding of the path, not a confidence score. Programmatic → green. LLM with context → yellow. LLM without context → red. Refusals → none.

Oneshot1System prompt quality is everything — it's the only thing constraining the LLM.

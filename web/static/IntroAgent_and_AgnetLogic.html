Quick Introduction to AI Agents and Agent Workflows

An AI Agent is a flexible, autonomous software system that facilitates the interaction between users and computer systems. Unlike traditional applications with rigid interfaces, AI Agents may accept different input types, including natural language, interpret the user's intent, execute the appropriate actions, and deliver results — adapting their behaviour to each situation.

This document first presents a general model for AI Agents. It then shows how each stage of the model is implemented as code components in the TOMMI Agentic Platform. Finally, it describes the different types of agents available in the platform.

Part 1 — A General Model for AI Agents

How do AI Agents work?

According to the classic AI agent framework (Russell & Norvig, 1995) [2], every agent follows three basic stages: Perception → Reasoning → Action. Here, we add a fourth stage — Production — to distinguish executing the task (e.g., querying a database, calling a language model) from producing the output (e.g., rendering a map, formatting a table, adding reliability indicators). Thus, according to this proposal, the stages of every AI agent are the following:

1. Perception
The user's input
➔
2. Reasoning
Understand the request
➔
3. Action
Execute the action
➔
4. Production
Produce the output

Intuitive Examples of Each Stage

StageWhat happensEveryday analogy
1. Perception The agent accepts the user's input: a typed question, a button click, a form selection, or a voice command. A librarian hears your question at the desk.
2. Reasoning The agent analyses the input to understand what the user wants and decides which action to take. This may be trivial (pass to the LLM) or complex (classify the query type, select data sources, detect intent). The librarian decides whether to look in the catalogue, the encyclopaedia, the archives, or simply answer from memory.
3. Action The agent executes one or more actions: query a database, search documents, call a language model, generate a chart, compute a result, or decline a request. The librarian walks to the shelf, finds the book, and reads the relevant passage.
4. Production The agent produces the output for the user: text, a table, a map, a chart, or a polite explanation of why it cannot help. A reliability indicator may be added. The output format depends on the interface and the type of result. The librarian returns to the desk and gives you the answer, noting whether it came from a trusted reference or a less reliable source.

Not every agent uses artificial intelligence in every stage. Some agents use AI only for Reasoning (understanding the question), others use it only for Action (generating text), and some use no AI at all — relying on rules and structured data throughout.

Note: This four-stage model is a conceptual abstraction for understanding agent behaviour. In practice, the boundaries between stages may overlap — for example, context retrieval serves both Reasoning (deciding what is relevant) and Action (querying a data store). Simpler agents may have minimal Reasoning, while complex agents may interleave multiple stages. The model is most useful as a framework for explaining what an agent does, not as a rigid architectural blueprint.

Design Insight: Handling Reliability

Reliability is a central challenge in AI agent design. As Rabanser et al. (2025) argue, "reliability is not a single property but a multidimensional concept" that encompasses correctness, consistency, robustness, and transparency [1]. An agent may produce a correct answer for one query and hallucinate on a similar one — and the user has no way to tell the difference unless the system provides reliability signals.

In the TOMMI platform, reliability is addressed through two complementary mechanisms: (1) minimising LLM dependence by routing queries to programmatic, deterministic response paths whenever possible, and (2) reliability cues — visual indicators that communicate to the user how much the response depends on AI interpretation vs. verified data. The cue colour reflects the structural grounding of the response path, not a confidence score.

The reliability of an AI agent's response correlates with the amount of relevant, controlled context provided to the LLM. Three factors determine this:

FactorDescriptionEffect on reliability
Context relevanceDoes the injected context (retrieved chunks, glossary entries, paper data) match the user's query?High relevance → LLM is constrained to accurate information → lower hallucination risk
Context volumeHow much relevant data is injected into the LLM prompt?More relevant context → LLM has more material to draw from → less need to invent
Instruction qualityHow well do the system prompt rules constrain the LLM? (e.g., "only answer from provided context", "say you don't know if uncertain")Stricter rules → LLM less likely to hallucinate beyond the context

This suggests a spectrum from green (fully grounded) to red (poorly grounded):

CueGrounding levelExamples
GreenProgrammatic. The response is built directly from structured data files, without involving the LLM. The agent reads the data, formats it, and presents it to the user. Since no AI interpretation is involved, the response is 100% faithful to the source data."Papers by Rubén González" → the agent looks up the name in a researchers file and returns the exact list of papers, affiliations, and topics stored there.

"What is the TAILOR project?" → the agent finds the project in a structured file and returns its title, grant ID, funder, budget, and participants exactly as recorded.

"What is explainable AI?" → the agent finds the term in a curated glossary and returns the expert-written definition verbatim.
YellowLLM well-grounded. The LLM generates the response, but it has been given relevant data as context (retrieved document chunks, paper lists, or a detailed system prompt). The AI interprets and summarises this data, so the response is informed but may not be perfectly faithful to the source."What are the main research topics at THUAS?" → the agent retrieves relevant papers and provides them to the LLM, which writes a summary. The paper list is real, but the summary is AI interpretation.

"Improve this prompt: You are a helpful assistant" (Oneshot) → the LLM has a detailed system prompt that guides its response, but no external data. The quality depends on the prompt.
RedLLM poorly grounded. The topic has little or no representation in the available data. The LLM must reason from its own general knowledge or infer what is absent from the database — both are inherently speculative."What responsible AI topics have not been studied?" → the agent provides the list of known topics, and the LLM must reason about what is missing — a speculative task with high hallucination risk.

"What is predictive policing?" → the term is not in the glossary or database, so the LLM answers from general knowledge without any grounding data.

A note on dynamic scoring

At least theoretically, reliability could be computed dynamically — for example, based on the number of retrieved chunks or their relevance scores. However, this would introduce instability (the same query could get different cues each time), arbitrary thresholds, and user confusion. It would also create a transparency paradox: a black-box estimation inside the transparency system itself. Instead, TOMMI assigns cues based on query type, which is determined by the deterministic classification chain — making the cue predictable, explainable, and stable.

Implications for agent design

When designing a new agent, developers should consider how each response path is grounded:

  • Maximise programmatic responses (green) for queries that can be answered from structured data — these are 100% reliable and fast.
  • Ensure the system prompt rules are specific and constraining — generic prompts lead to more hallucination.
  • For RAG agents, the quality of the knowledge base and the retrieval method (BM25 vs vector) directly affect response reliability.
  • Assign red cues to response paths where the LLM must reason beyond the available data (gap analysis, out-of-glossary concepts).
  • Never show a reliability cue for honest refusals (off-topic, non-research) — a refusal is not unreliable content.

The four dimensions of reliability in TOMMI

Rabanser et al. [1] identify four dimensions of AI agent reliability. The following table analyses how each dimension is currently addressed in TOMMI and where improvements could be made:

DimensionDefinitionHow TOMMI addresses itLimitations & opportunities
Correctness Is the response factually accurate?
  • Programmatic paths (8 of 13 in Metadata+RAG) are correct by construction — the data comes directly from curated files, with no LLM interpretation.
  • Paper verification in post-processing checks every cited title and ID against papers.json, flagging unrecognised references.
  • SQL verification in Text2SQL checks table/column existence and semantic alignment before executing any query.
  • Authority sanitisation replaces overconfident LLM phrases ("has not been studied") with accurate ones ("does not appear in the indexed database").
 Correctness is strongest on programmatic paths and weakest on gap analysis (red cue). A remaining challenge is verifying correctness of LLM-generated commentary on topic searches — the paper list is verified but the summary is not.
Consistency Does the same query always produce the same answer?
  • Programmatic paths are perfectly consistent — the same query always produces the identical response (deterministic code, no randomness).
  • Classification chain is rule-based: the same query always follows the same response path.
  • Reliability cues are determined by query type, not by LLM output — so the same query always gets the same cue.
 LLM paths are inherently inconsistent — the same question may get different wording each time due to sampling. This could be mitigated by setting temperature=0 or by caching LLM responses for repeated queries. The more response paths are programmatic, the more consistent the agent is overall.
Robustness Does the agent handle rephrased queries, edge cases, and unexpected inputs correctly?
  • Pattern-based detection uses multiple variants per intent (e.g., researcher lookup matches full name, surname, first+surname, with word boundaries to avoid false positives like "pons" in "responsible").
  • Bilingual patterns in Text2SQL handle both Spanish and English inputs for every intent.
  • Decision logic benchmark (56 test cases) verifies that the classification chain correctly routes queries.
  • Off-topic detection is placed last in the priority chain so that legitimate queries (projects, researchers) are never misclassified.
 Pattern-based detection can miss novel phrasings — e.g., "Give me the bibliography of professor Smith" might not match researcher patterns. This could be improved with broader pattern sets or a lightweight intent classifier. The benchmark should be expanded with adversarial examples.
Transparency Can the user understand how trustworthy the response is?
  • Reliability cues (green/yellow/red/none) signal the trustworthiness of each response based on its source — whether it comes from verified data, AI interpretation, or speculation.
  • Crystal box mode in Text2SQL shows the generated SQL query and a plain-language explanation, so the user can verify the AI translation.
  • Open documentation of the agent's internal logic (this document) makes the decision process publicly visible and auditable.
 Transparency could be deepened by indicating which specific data sources contributed to each response, and by showing the retrieved chunks alongside RAG responses so users can verify grounding directly.

The key architectural insight is that programmatic response paths score high on all four dimensions simultaneously: they are correct (data from source), consistent (deterministic), robust (pattern-based classification is testable), and transparent (the response path is visible). Each query type moved from an LLM path to a programmatic path improves reliability across all four dimensions at once.

Response Paths: A Methodology for Agent Development

A response path is the complete route a query takes through the four stages (Perception → Reasoning → Action → Production). Each agent type can be characterised by the number and kind of response paths it supports. This offers a practical methodology for developing a new agent: start with the simplest response paths and progressively add more complex ones.

Phase 1 — Single path (Oneshot)

Begin with a single response path: every query goes directly to the LLM with a system prompt. This is the fastest way to get a working agent. Focus on:

  • Writing a clear, constraining system prompt (identity, rules, scope)
  • Testing with representative queries to verify the LLM stays on topic
  • All responses get the same reliability cue (yellow) — or hide cues entirely
Result: 1 response path. Reliability: Yellow (all LLM).

Phase 2 — Add retrieval (RAG)

Add a knowledge base (documents, markdown files) and a retrieval mechanism (BM25 keyword search or ChromaDB vector search). Now the LLM receives relevant context alongside the system prompt. Focus on:

  • Preparing and chunking the knowledge base
  • Tuning the number of retrieved chunks (too few = hallucination, too many = noise)
  • Adding an off-topic check in Production to detect refusals and suppress cues for them
Result: 2 response paths (on-topic → Yellow, off-topic refusal → None).

Phase 3 — Add programmatic early returns

Identify query types that can be answered without the LLM — these are faster, cheaper, and 100% reliable. Typical early returns:

  • Meta-questions ("What can you do?") → build response from config.json
  • Non-research tasks ("Write me an essay") → fixed refusal message
  • Off-topic queries ("What is the weather?") → programmatic refusal listing in-scope topics

Each early return adds a new response path with its own reliability cue (typically none, since refusals and meta-responses are not content claims).

Result: 4–5 response paths. New paths are None (no cue for honest responses).

Phase 4 — Add structured data paths

If the agent has access to structured data (JSON files, databases, glossaries), add programmatic response paths that format this data directly — bypassing the LLM entirely. Examples:

  • Researcher lookup → format papers, topics, affiliations from researchers.json
  • Project queries → format title, grant ID, funder, budget from project_docs/
  • Glossary definitions → return expert-written text from markdown
  • Figure/map requests → build visualisation link from regex extraction

These are the most valuable paths to add: they produce Green (verified data) responses and eliminate hallucination risk for common queries. Each path requires a detection function (pattern matching in the Reasoning stage) and a formatting function (data presentation in Production).

Result: 8–10 response paths. New paths are Green (programmatic).

Phase 5 — Add mixed paths and navigation

For more complex agents, add paths that combine programmatic data with LLM interpretation, and navigation features for result sets:

  • Topic search → programmatic paper list (Green) + LLM analytical commentary (Yellow)
  • Gap analysis → LLM reasons about absences in the data (Red)
  • Result navigation → show more, sort, filter, expand detail (no LLM, None)
  • Query refinement → LLM modifies previous SQL/search (Yellow)
Result: 13+ response paths. Full spectrum of reliability cues.

Summary: progressive path development

PhaseAgent typePathsKey additionCues used

2RAG2Knowledge base + retrievalY —
3RAG + early returns4–5Programmatic refusalsY —

This progression reflects a fundamental trade-off: more response paths mean more development effort, but also higher reliability and lower LLM costs. Each programmatic path added is one fewer query that needs the LLM — making the agent faster, cheaper, and more trustworthy.

How Reasoning Varies Across Agent Types

The Reasoning stage is where the most significant architectural differences between agent types emerge. In simple agents, it is mechanical — the agent does very little analysis before acting. In complex agents, reasoning is a multi-step decision process that determines which data sources to use and which actions to perform.

Agent typeReasoning implementationComplexity
Oneshot None. The query is passed directly to the LLM with the system prompt. No classification, no retrieval, no decision-making. Every query follows the same path. ⬜
RAG Mechanical retrieval. The query is converted to a vector embedding and used to find similar document chunks in ChromaDB. The retrieval is automatic — there is no decision about what kind of question it is. ⬜⬜
RAG Vectorless Keyword retrieval. Same as RAG but uses BM25 keyword matching instead of vector similarity. The only decision is a post-hoc check: was the response off-topic? ⬜⬜
Text2SQL Intent detection. The agent first checks whether the user is navigating existing results (show more, sort, go back, expand a row) or asking a new question. Navigation intents are handled directly without the LLM. New questions go through SQL translation and verification. ⬜⬜⬜
Metadata+RAG (EH) Multi-step classification. The agent runs a priority chain of 12 checks to determine the query type: meta-question, off-topic, conceptual, project, researcher, topic search, gap analysis, figure request, etc. Each type is routed to a different data source and action. This is the most sophisticated reasoning in TOMMI. ⬜⬜⬜⬜⬜

Metadata+RAG Agents (Excellence Hubs)

The most complex TOMMI agent type, used for the UNINOVIS Excellence Hubs. Combines structured metadata (papers, researchers, projects, glossary) with document retrieval, interactive maps, and a multi-step decision logic. Unlike simpler agents (which have 1–2 response paths), Metadata+RAG agents have 6 distinct response paths, each with different actions, production outputs, and reliability cues.

1. Perception

The agent receives the user's text query via the chat interface. It also receives session context: conversation history, session ID, model preference, and transparency level. LLM: Not used.

2. Reasoning

A priority chain of 13 classification checks identifies which response path the query should follow. The first match wins. This is where the agent's intelligence resides — it determines not just the answer, but the entire processing path (which data source to use, whether the LLM is needed, and which reliability cue to assign). The entire classification chain is rule-based and deterministic. LLM: Not used.

3. Action & 4. Production (path-specific)

Each response path has its own action and production. This is the key architectural difference from simpler agent types:

RAG agents use ChromaDB vector embeddings to find semantically similar document chunks. Unlike BM25 (keyword matching), vector retrieval can find relevant content even when the exact words differ — e.g., "adversarial testing" matches "red-teaming".

1. Perception

The agent receives the user's text query via the chat interface.

2. Reasoning

The query is converted into a vector embedding and used to search ChromaDB for semantically similar document chunks. This is mechanical — no classification of query type, no decision-making. LLM: Not used (embedding model is separate from the generative LLM).

3. Action

LLM: Always used. The LLM receives three inputs combined into a single prompt: the system prompt (agent identity and rules), the retrieved document chunks (context), and the user's query. The LLM generates an answer constrained to this context. Every query goes to the LLM — there is no programmatic path.

Example: what the LLM receives

For a query like "What is explainable AI?" on a Responsible AI agent, the LLM prompt is assembled as follows:

── System prompt (from prompts.json) ────────────── You are a research assistant for the UNINOVIS Excellence Hub on Responsible AI. Answer only from the provided context. If the answer is not in the context, say so. ── Retrieved chunks (from ChromaDB / BM25) ──────── --- Chunk 1 --- Explainable AI (XAI) refers to methods and techniques that make the outputs of AI systems understandable to humans. The EU AI Act requires high-risk AI systems to provide explanations of their decisions... --- Chunk 2 --- Key XAI techniques include LIME (Local Interpretable Model-agnostic Explanations), SHAP (SHapley Additive exPlanations), and attention visualisation... --- Chunk 3 --- The relationship between explainability and trust is well documented. Users who understand why an AI system made a decision are more likely to trust it... ── User query ────────────────────────────────────── What is explainable AI?

The LLM can only "see" the content above. It cannot access the database, the internet, or any other data. The quality of the response depends entirely on whether the retrieved chunks contain relevant information.

4. Production

The LLM response is post-processed (humility hedging, authority sanitisation) and delivered with a reliability cue. LLM: Not used — post-processing is rule-based.

1. Perception

The agent receives the user's text query via the chat interface.

2. Reasoning

The query is tokenised (split into words, stop words removed) and scored against all document chunks using BM25 keyword matching. The top N chunks with the highest scores are selected as context. This is mechanical — no classification of query type. LLM: Not used.

3. Action

LLM: Always used. The LLM receives three inputs combined into a single prompt: the system prompt (agent identity and rules), the retrieved document chunks (context found by BM25 keyword matching), and the user's query. The LLM generates an answer constrained to this context. Every query goes to the LLM — there is no programmatic path.

Example: what the LLM receives

For a query like "How do I deploy an agent?" on the Tommi Tutor agent, the LLM prompt is assembled as follows:

── System prompt (from prompts.json) ────────────── You are Tommi Tutor, a support assistant for the TOMMI Agentic Platform. Answer questions about deploying, configuring, and testing AI agents. Use only the provided context. ── Retrieved chunks (BM25 keyword match) ────────── --- Chunk 1 (score: 8.4) --- To deploy an agent, create a directory under agents/ with agent.py, app.py, config.json, and prompts.json. The config.json file defines the agent's name, type, LLM provider, and data sources... --- Chunk 2 (score: 6.1) --- After creating the agent files, register it in the web server by adding an import and mount statement in web/app.py. Restart the server to load the new agent... --- Chunk 3 (score: 4.7) --- Agent types available: rag_vectorless (BM25 keyword retrieval), rag_metadata_vectorless (structured metadata + BM25), text2sql (natural language to SQL), oneshot (no retrieval)... ── User query ────────────────────────────────────── How do I deploy an agent?

Unlike ChromaDB (vector search), BM25 matches chunks by keyword overlap — the query words "deploy" and "agent" match directly against the chunk text. Chunks are ranked by BM25 score and the top N are selected. The LLM can only "see" these chunks and must answer from them.

4. Production

The first 300 characters of the response are checked for off-topic refusal phrases. If detected, no banner is shown (honest refusal). Otherwise, a yellow "AI Commentary" banner is added. LLM: Not used — post-processing is rule-based.

Reliability Cues

Response typeCueRationale
On-topic response (LLM interprets retrieved chunks)YellowAI interpretation — the LLM generates from retrieved context, which may be incomplete or misinterpreted
Off-topic refusal (detected in first 300 chars)NoneHonest refusal is not unreliable content

RAG Vectorless agents do not use green cues (no structured metadata to serve programmatically) or red cues (no gap analysis capability). The off-topic detector scans only the first 300 characters to avoid false positives when the response quotes off-topic phrases in explanations.

Text2SQL Agents (Pisha, Algoria)

Text2SQL agents convert natural language to SQL queries. Unlike Oneshot and RAG agents (which have a single response path), Text2SQL agents have three distinct response paths, each with different actions and production outputs. The Reasoning stage determines which path the query follows.

1. Perception

The agent receives the user's text query. It also maintains session state: previous SQL query, previous results, operations history, and shown fields. LLM: Not used.

2. Reasoning

An 8-step intent detection chain identifies which response path the query should follow. The first match wins. This is where the agent's decision logic resides — it determines not just the answer, but the entire processing path. LLM: Not used — intent detection is pattern-based.

3. Action & 4. Production (path-specific)

Unlike simpler agents where every query follows the same action and production, here each response path has its own action and production:

Response pathReasoningActionProduction
New query No navigation or refinement pattern detected LLM generates SQL from DB schema + user query → verify → execute on SQLite DB HTML table + Yellow cue + SQL display (crystal box)
Refinement Refinement pattern detected + previous SQL exists LLM modifies previous SQL → verify → execute on SQLite DB HTML table + Yellow cue + SQL display (crystal box)
Navigation Show more, detail, back, history, show field, or sort detected Read from session state — no DB access, no LLM Re-render table or detail card. No cue

This is the key architectural difference from simpler agent types: the Reasoning stage does not just classify the query — it selects the entire response path, including which Action to perform and which Production output to generate.

Action detail: New query path (step 8)

Unlike RAG agents (where the LLM generates a text answer), the Text2SQL Action stage involves two sub-steps: first the LLM translates the question to SQL, then the SQL is executed on the database. The LLM never sees the data — it only sees the schema.

Sub-step 1: LLM translates question → SQL

── System prompt ─────────────────────────────────── You are a SQL expert. Convert the user's question into a SQLite SELECT query. Use only the tables and columns described in the schema below. ── Database schema (injected as context) ─────────── TABLE: destinations host_institution TEXT -- University name destination_country TEXT -- Country name lang_1_name TEXT -- Required language lang_1_cert_level TEXT -- Language level (B1, B2...) student_vacancies INTEGER -- Number of places mobility_program TEXT -- Erasmus+, bilateral... uma_faculties TEXT -- Faculty at UMA uma_degrees TEXT -- Degree programme ── User query ────────────────────────────────────── Agreements with universities in Germany that require English B2

The LLM responds with:

SELECT * FROM destinations WHERE destination_country = 'Germany' AND lang_1_name = 'English' AND lang_1_cert_level = 'B2' ORDER BY host_institution;

Sub-step 2: Verify SQL → Execute on SQLite database

The generated SQL is verified (table/column existence, semantic alignment with the question) and then executed directly on the SQLite database. The results come from the DB, not from the LLM — the LLM was only used as a translator.

── Verification ──────────────────────────────────── ✓ Table "destinations" exists ✓ Columns "destination_country", "lang_1_name", "lang_1_cert_level" exist ✓ Semantic check: "Germany" → destination_country ✓ "English B2" → lang_1_name + level ✓ ── Execution on SQLite DB ────────────────────────── → 12 rows returned

This is why the reliability cue is Yellow: the data is real (from the database), but the translation is AI — the LLM may have misunderstood the question. In Crystal box mode, the SQL and a plain-language explanation are shown so the user can verify the translation.

Oneshot agents process each query independently with no conversation memory, no document retrieval, and no structured data. They rely entirely on the system prompt and the LLM.

1. Perception

The agent receives the user's text query via the chat interface. Each query is independent — there is no conversation memory.

2. Reasoning

None. The query is passed directly to the LLM without any classification, retrieval, or decision-making. Every query follows exactly the same path. LLM: Not used in this stage.

3. Action

LLM: Always used. The LLM generates a response using only the system prompt (identity + rules) and the user's query. No documents, no database, no external data. This is the simplest possible agent — every query goes to the LLM.

Example: what the LLM receives

For a query like "Improve this prompt: You are a helpful assistant that answers questions" on the Prompt Assistant agent, the LLM receives:

── System prompt (from prompts.json) ────────────── You are PROMPT Assistant, a specialist in writing and improving system prompts for AI agents running on TOMMI. Your sole purpose is to help users craft prompts that make their agents clearer, more focused, and more effective. When given a prompt to review, you diagnose specific weaknesses and deliver a concrete rewrite. GUIDELINES: 1. When reviewing a prompt, start with what works before listing problems. 2. Always deliver a rewritten version — diagnosis without a fix is not enough. 3. Structure rewrites using the Identity / Rules / Strict format whenever it fits. ... ── No retrieved chunks ───────────────────────────── (Oneshot agents have no knowledge base — the LLM relies entirely on the system prompt and its own general knowledge) ── User query ────────────────────────────────────── Improve this prompt: You are a helpful assistant that answers questions

Note the contrast with RAG agents: there are no retrieved chunks. The LLM has only the system prompt to guide its behaviour. The quality of the response depends entirely on how well the system prompt constrains the LLM and on the LLM's own general knowledge.

4. Production

The LLM's text response is delivered directly to the user. No post-processing pipeline. LLM: Not used in this stage.

Controlled by the reliability_cues setting in config.json ("shown" / "hidden"). Since Oneshot agents have no database or document retrieval, the cue is always yellow. Most deployments set it to hidden to avoid redundancy.

When to use Oneshot

Oneshot agents are appropriate when:

  • The task does not require a knowledge base (e.g., prompt writing, brainstorming)
  • Each query is self-contained — no follow-up needed
  • The LLM's general knowledge is sufficient
  • Speed is important (no retrieval overhead)

For tasks requiring grounded, verifiable answers from specific data, use RAG or Metadata+RAG agents instead.

TOMMI Agent Decision Logic

When a user asks a question, a TOMMI agent does not simply forward it to the language model. Instead, it first classifies the question and selects the right data source. This page visualises the decision logic, reliability cue assignment, and post-processing pipeline.

The Four Stages of Every Agent

Every TOMMI agent — regardless of type — follows the same four stages when processing a user request:

1. Receive
The user's input
➔
2. Interpret
Understand the request
➔
3. Act
Execute the action
➔
4. Respond
Deliver the output

Common Vocabulary

TermDefinition
ReceiveThe agent accepts the user's input. This can be natural language text, a form selection, a button click, or a follow-up to a previous conversation.
InterpretThe agent analyses the input to decide what to do. This is the agent's decision logic. Depending on the agent type, interpretation can range from purely mechanical (pass everything to the LLM) to a sophisticated multi-step classification that routes different questions to different actions. See the comparison below.
ActThe agent executes one or more actions: query a database, search documents, call a language model, generate a visualisation, or refuse a request. An agent may combine several actions in a single response (e.g., retrieve data from the database AND ask the LLM to comment on it).
RespondThe agent formats the result and delivers it to the user: text, a table, a map, a chart, or a message explaining why it cannot help. A reliability cue (coloured banner) may be added to indicate how trustworthy the response is.
System promptInstructions given to the LLM that define the agent's identity, rules, and constraints. Only relevant when the Act stage involves an LLM call.
ContextData retrieved from the knowledge base (documents, metadata, glossary) and injected into the LLM prompt. The LLM can only "see" what the context provides — it does not access the database directly.
Reliability cueA coloured banner (🟢 green, 🟡 yellow, 🔴 red, or none) that indicates the source and trustworthiness of the response. Assigned based on how the response was generated.
Post-processingSteps applied to the LLM output before delivering it to the user: authority sanitisation, paper verification, humility hedging, etc.

What Does "Interpret" Mean in Practice?

The Interpret stage varies dramatically across agent types. In simple agents, it is mechanical — the agent does very little analysis before acting. In complex agents, interpretation is a multi-step decision process that determines which data sources to use and which actions to perform.

Agent typeInterpretationComplexity
Oneshot None. The query is passed directly to the LLM with the system prompt. No classification, no retrieval, no decision-making. Every query follows the same path. ⬜
RAG Mechanical. The query is converted to a vector embedding and used to find similar document chunks. The retrieval is automatic — there is no decision about what kind of question it is. ⬜⬜
RAG Vectorless Mechanical. Same as RAG but uses BM25 keyword matching instead of vectors. The only decision is a post-hoc check: was the response off-topic? If so, remove the banner. ⬜⬜
Text2SQL Intent detection. The agent first checks whether the user is navigating existing results (show more, sort, go back, expand a row) or asking a new question. Navigation intents are handled without the LLM. New questions go through SQL translation and verification. ⬜⬜⬜
Metadata+RAG (EH) Multi-step classification. The agent runs a priority chain of 12 checks to determine the query type: meta-question, off-topic, conceptual, project, researcher, topic search, gap analysis, figure request, etc. Each type is routed to a different data source and action. This is the most sophisticated interpretation in TOMMI. ⬜⬜⬜⬜⬜

RAG Agents Flow (Vector-based retrieval)

RAG agents use ChromaDB vector embeddings to find semantically similar document chunks. Unlike BM25 (keyword matching), vector retrieval can find relevant content even when the exact words differ — e.g., "adversarial testing" matches "red-teaming".

RAG (Vector) agents use claim-level grounding analysis: each claim in the response is checked against the retrieved context and scored. This produces reliability labels (High / Good / Poor) rather than the procedural banners (Verified / AI Commentary / Unverified) used by Vectorless agents.

Simple agents do not use green banners (no structured metadata) or red banners (no gap analysis). The off-topic detector scans only the first 300 characters to avoid false positives when the response quotes off-topic phrases in explanations.

Intent Detection

Before converting a query to SQL, the agent checks whether the user is navigating or refining previous results. If so, it handles the action directly without calling the LLM:

IntentExampleActionNeeds LLM?
Show more"Show me more", "next results"Display next page of previous resultsNo
Detail request"Show details of #3", "expand #5"Show full details of a specific resultNo
Sort"Sort by country A-Z", "order by date"Re-sort and re-display current resultsNo
Show field"Show language requirements"Add a column to current resultsNo
Back"Go back", "previous search"Restore previous result setNo
Refinement"Only those in Italy", "only with B2"Add WHERE clause to previous SQLPartial (modifies SQL)
New query"Show agreements with The Hague"Full Text-to-SQL conversionYes

This intent detection avoids unnecessary LLM calls for navigation actions, making the agent faster and more responsive. Only genuinely new queries or refinements require the LLM.

When to use Oneshot

Oneshot agents are appropriate when:

  • The task does not require a knowledge base (e.g., prompt writing, brainstorming)
  • Each query is self-contained — no follow-up needed
  • The LLM's general knowledge is sufficient
  • Speed is important (no retrieval overhead)

For tasks requiring grounded, verifiable answers from specific data, use RAG or Metadata+RAG agents instead.

AI Agent Decision Logic

An AI Agent is a flexible, autonomous software system that facilitates the interaction between users and computer systems. Unlike traditional applications with rigid interfaces, AI Agents may accept different input types, including natural language, interpret the user's intent, execute the appropriate actions, and deliver results — adapting their behaviour to each situation.

This document first presents a general model for AI Agents. It then shows how each stage of the model is implemented as code components in the TOMMI Agentic Platform. Finally, it describes the different types of agents available in the platform.

Part 1 — A General Model for AI Agents

How do AI Agents work?

According to the classic AI agent framework (Russell & Norvig, 1995), every agent follows three basic stages: Perception → Reasoning → Action. Here, we add a fourth stage — Production — to distinguish executing the task (e.g., querying a database, calling a language model) from producing the output (e.g., rendering a map, formatting a table, adding reliability indicators). Thus, according to this proposal, the stages of every AI agent are the following:

1. Perception
The user's input
➔
2. Reasoning
Understand the request
➔
3. Action
Execute the action
➔
4. Production
Produce the output

Intuitive Examples of Each Stage

StageWhat happensEveryday analogy
1. Perception The agent accepts the user's input: a typed question, a button click, a form selection, or a voice command. A librarian hears your question at the desk.
2. Reasoning The agent analyses the input to understand what the user wants and decides which action to take. This may be trivial (pass to the LLM) or complex (classify the query type, select data sources, detect intent). The librarian decides whether to look in the catalogue, the encyclopaedia, the archives, or simply answer from memory.
3. Action The agent executes one or more actions: query a database, search documents, call a language model, generate a chart, compute a result, or decline a request. The librarian walks to the shelf, finds the book, and reads the relevant passage.
4. Production The agent produces the output for the user: text, a table, a map, a chart, or a polite explanation of why it cannot help. A reliability indicator may be added. The output format depends on the interface and the type of result. The librarian returns to the desk and gives you the answer, noting whether it came from a trusted reference or a less reliable source.

Not every agent uses artificial intelligence in every stage. Some agents use AI only for Reasoning (understanding the question), others use it only for Action (generating text), and some use no AI at all — relying on rules and structured data throughout.

Note: This four-stage model is a conceptual abstraction for understanding agent behaviour. In practice, the boundaries between stages may overlap — for example, context retrieval serves both Reasoning (deciding what is relevant) and Action (querying a data store). Simpler agents may have minimal Reasoning, while complex agents may interleave multiple stages. The model is most useful as a framework for explaining what an agent does, not as a rigid architectural blueprint.

How Reasoning Varies Across Agent Types

The Reasoning stage is where the most significant architectural differences between agent types emerge. In simple agents, it is mechanical — the agent does very little analysis before acting. In complex agents, reasoning is a multi-step decision process that determines which data sources to use and which actions to perform.

Agent typeReasoning implementationComplexity
Oneshot None. The query is passed directly to the LLM with the system prompt. No classification, no retrieval, no decision-making. Every query follows the same path. ⬜
RAG Mechanical retrieval. The query is converted to a vector embedding and used to find similar document chunks in ChromaDB. The retrieval is automatic — there is no decision about what kind of question it is. ⬜⬜
RAG Vectorless Keyword retrieval. Same as RAG but uses BM25 keyword matching instead of vector similarity. The only decision is a post-hoc check: was the response off-topic? ⬜⬜
Text2SQL Intent detection. The agent first checks whether the user is navigating existing results (show more, sort, go back, expand a row) or asking a new question. Navigation intents are handled directly without the LLM. New questions go through SQL translation and verification. ⬜⬜⬜
Metadata+RAG (EH) Multi-step classification. The agent runs a priority chain of 12 checks to determine the query type: meta-question, off-topic, conceptual, project, researcher, topic search, gap analysis, figure request, etc. Each type is routed to a different data source and action. This is the most sophisticated reasoning in TOMMI. ⬜⬜⬜⬜⬜

1. Perception

The agent receives the user's text query via the chat interface. It also receives session context (conversation history, session ID, model preference, transparency level).

2. Reasoning

This is where the agent's intelligence resides. A priority chain of 12 classification checks determines the query type: meta-question, off-topic, conceptual, project, researcher, topic search, gap analysis, figure request, etc. The first match wins. Based on the classification, the agent selects the appropriate data source and builds context. See the detailed classification and context chain below.

3. Action

Depends on the query type identified during Reasoning. May include: querying papers.json or researchers.json directly (no LLM), calling the LLM with system prompt + context, generating a map link, building a programmatic factual section, or simply refusing an off-topic request. Some responses combine multiple actions (e.g., a verified paper list + LLM commentary).

4. Production

The output depends on the query type: it may be a formatted text response (paper listings, glossary definitions, commentary), an interactive map or figure (publications map, collaboration network, project distribution), a structured list (researchers, projects), or a polite refusal. When the output involves text generated by the LLM, it passes through a processing pipeline: authority sanitisation, paper title verification, unsolicited gap detection, and humility hedging. The reliability cue (green, yellow, red, or none), already determined during Reasoning based on the query type, is displayed as a coloured banner at the top of the response. The result is streamed to the user via Server-Sent Events.

RAG Agents (Vector-based retrieval)

RAG agents use ChromaDB vector embeddings to find semantically similar document chunks. Unlike BM25 (keyword matching), vector retrieval can find relevant content even when the exact words differ — e.g., "adversarial testing" matches "red-teaming".

Perception
User query
➔
Reasoning
Embed query as vector,
find similar chunks in ChromaDB
➔
Action
LLM generates answer
from system prompt + context
➔
Production
Post-processing,
humility + reliability cues

1. Perception

The agent receives the user's text query via the chat interface.

2. Reasoning

The query is converted into a vector embedding and used to search ChromaDB for semantically similar document chunks. This is mechanical — no classification of query type, no decision-making. The retrieval is automatic.

3. Action

The retrieved document chunks are injected as context into the system prompt. The LLM generates an answer constrained to this context.

4. Production

The LLM response is post-processed (humility hedging, authority sanitisation) and delivered with reliability cues (High / Good / Poor) based on claim-level grounding analysis.

RAG (Vector) agents use claim-level grounding analysis: each claim in the response is checked against the retrieved context and scored. This produces reliability labels (High / Good / Poor) rather than the procedural banners (Verified / AI Commentary / Unverified) used by Vectorless agents.

1. Perception

The agent receives the user's text query via the chat interface.

2. Reasoning

The query is tokenised (split into words, stop words removed) and scored against all document chunks using BM25 keyword matching. The top N chunks with the highest scores are selected as context. This is mechanical — no classification of query type.

3. Action

The retrieved chunks are injected as context into the system prompt. The LLM generates an answer constrained to this context.

4. Production

The first 300 characters of the response are checked for off-topic refusal phrases. If detected, no banner is shown (honest refusal). Otherwise, a yellow "AI Commentary" banner is added. The response is then delivered to the user.

Banner Logic

ConditionBanner
On-topic response (context found)Yellow AI Commentary
Off-topic refusal detectedNone

Simple agents do not use green banners (no structured metadata) or red banners (no gap analysis). The off-topic detector scans only the first 300 characters to avoid false positives when the response quotes off-topic phrases in explanations.

1. Perception

The agent receives the user's text query. It also maintains session state (previous SQL, previous results) for navigation and refinement.

2. Reasoning — Intent Detection

Before converting a query to SQL, the agent checks whether the user is navigating or refining previous results. If so, it handles the action directly without calling the LLM:

IntentExampleActionNeeds LLM?
Show more"Show me more", "next results"Display next page of previous resultsNo
Detail request"Show details of #3", "expand #5"Show full details of a specific resultNo
Sort"Sort by country A-Z", "order by date"Re-sort and re-display current resultsNo
Show field"Show language requirements"Add a column to current resultsNo
Back"Go back", "previous search"Restore previous result setNo
Refinement"Only those in Italy", "only with B2"Add WHERE clause to previous SQLPartial (modifies SQL)
New query"Show agreements with The Hague"Full Text-to-SQL conversionYes

This intent detection avoids unnecessary LLM calls for navigation actions, making the agent faster and more responsive. Only genuinely new queries or refinements require the LLM.

3. Action

For new queries: the LLM translates the natural language question into SQL. The SQL is then verified (table/column existence, semantic match) and executed against the SQLite database. For navigation intents (show more, sort, back): the action is handled directly from session state without calling the LLM.

4. Production

Results are formatted as HTML tables with expandable details. Transparency cues indicate the AI translation risk (yellow) and verified data from the database (green). In Crystal box mode, the SQL query and a plain-language explanation are shown alongside the results.

Oneshot Agents (Prompt Assistant)

Oneshot agents process each query independently with no conversation memory, no document retrieval, and no structured data. They rely entirely on the system prompt and the LLM.

1. Perception

The agent receives the user's text query via the chat interface. Each query is independent — there is no conversation memory.

2. Reasoning

None. The query is passed directly to the LLM without any classification, retrieval, or decision-making. Every query follows exactly the same path.

3. Action

The LLM generates a response using only the system prompt (identity + rules) and the user's query. No documents, no database, no external data.

4. Production

The LLM's text response is delivered directly to the user. No post-processing, no reliability cues (typically hidden for Oneshot agents).

When to use Oneshot

Oneshot agents are appropriate when:

  • The task does not require a knowledge base (e.g., prompt writing, brainstorming)
  • Each query is self-contained — no follow-up needed
  • The LLM's general knowledge is sufficient
  • Speed is important (no retrieval overhead)

For tasks requiring grounded, verifiable answers from specific data, use RAG or Metadata+RAG agents instead.
